The log · 15 October 2026

A timeout is not a failure

Slow runs were reported as broken ones, and two alarms fired on work that had already finished.

A timeout reported as a failure

What happenedTwo test runs on the tool that scores a property test suite against a bug's before-fix and after-fix code were killed at the time limit after 10m09s each, and both were reported as exit 1

LessonWhen a command is killed for running too long but reported as a failure, the builder looks for a bug that isn't there

What changedThe final test check now reports a killed command as a timeout, and a project can give its final command more time

Fuzzing ran past the time limit

What happenedThe after-fix side's tests alone took 1126.1s, nearly twice the 600s limit

LessonOn this project the random-input testing ran long, not the clone or the compile, so a faster build would not have fixed it

What changedThe director ruled that the runner lowers its number of fuzz runs and leaves the results file out of the change; neither was done in that build

A design alarm that fired on finished work

What happenedThe alarm that watches design work used a job name that never runs on the web projects, and it counted plans that were already done

LessonAn alarm that counts finished work reports a stall that isn't happening

What changedThe alarm no longer counts finished plans

Review alarms keyed on progress, not on reviews

What happenedThe code review alarms for Swift, Kotlin, Python, Ruby, Rust, Go and PHP could fire for any open plan that had moved past review, however long ago that review ran

LessonAn alarm should look for the event it watches, not for how far a plan has got

What changedThe seven alarms now fire only on a review that ran within the period they check
